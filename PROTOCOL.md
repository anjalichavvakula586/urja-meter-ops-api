# PROTOCOL.md — Urja Meter Ops Portal Investigation

## 1. Purpose

This document records the observed behavior of the Urja Meter Ops portal and the upstream requests used by the read-only API.

Portal: https://urja-ops.flockenergy.tech

The investigation was performed through normal browser use and Chrome DevTools Network inspection. The portal was accessed read-only. No attempt was made to modify portal records or bypass access controls.

This document separates directly observed behavior from assumptions and remaining unknowns.

## 2. Observed Portal Navigation

### Login

The portal login form was submitted using a POST request.

Observed request:

- Method: `POST`
- Path: `/login`
- Form encoding: URL-encoded form data
- Form field names: `email`, `password`
- Browser Network status: `200 OK`
- Response body indicated a redirect to `/meters` with status `303`

Observed response body:

```json
{
  "type": "redirect",
  "status": 303,
  "location": "/meters"
}
```

The response body describes the redirect generated by the portal's login action. The browser's Network status for the request itself was `200 OK`; these are not contradictory because the response body represents a framework-level redirect result.

Credentials and session-cookie values are intentionally not recorded in this document.

The displayed text `403 total` is a UI count, not evidence of an HTTP 403 response.

## 3. Verified Upstream Requests

The following request paths were copied from Chrome DevTools Network while logged into the portal. The requests were observed returning HTTP 200.

### 3.1 Meter Search

Observed request:

```http
GET /portal/meters/search?q=&page=1
```

Example full URL:

`https://urja-ops.flockenergy.tech/portal/meters/search?q=&page=1`

Observed meter-specific request:

`https://urja-ops.flockenergy.tech/portal/meters/search?q=J100000&page=1`

The search request returns meter summaries in a `data` array. An observed sample item was:

```json
{
  "meterId": "J100000",
  "serialNo": "SE33962",
  "make": "HPL",
  "phaseType": "single",
  "installStatus": "Decommissioned",
  "dtCode": "DT-001"
}
```

The public API maps these fields to snake_case:

- `meterId` → `meter_id`
- `serialNo` → `serial_no`
- `phaseType` → `phase_type`
- `installStatus` → `install_status`
- `dtCode` → `dt_code`

The API exposes the search query and requested page in its own response. The exact upstream pagination metadata and edge-case behavior have not been fully documented.

### 3.2 Meter Geographic Coordinates

Observed request:

```http
GET /portal/meters/J100000/geo
```

Example full URL:

`https://urja-ops.flockenergy.tech/portal/meters/J100000/geo`

Observed response:

```json
{
  "data": {
    "latitude": "26.938961002479868",
    "longitude": "75.83095696146852"
  }
}
```

The portal represents the coordinates as strings. The public API converts them to numbers and validates the geographic ranges.

### 3.3 Meter Energy Readings

Observed request:

```http
GET /portal/meters/J100000/energy
```

Example full URL:

`https://urja-ops.flockenergy.tech/portal/meters/J100000/energy`

Observed response shape:

```json
{
  "data": [
    {
      "timestamp": "23/06/2026 23:30",
      "kwh": "48438.74",
      "kvah": "52313.84",
      "voltR": "226"
    }
  ]
}
```

The example above shows one reading to illustrate the response shape. The live response inspected for `J100000` contained 337 readings.

Observed characteristics:

- Timestamp format: `DD/MM/YYYY HH:mm`
- Samples were spaced at 30-minute intervals
- Measurements were represented as strings
- The UI labels the measurements KWH, KVAH, and V(R)

The public API normalizes the measurement fields to numeric values where valid and uses `volt_r` for the voltage field. It preserves the original timestamp in `timestamp_raw`.

The API emits an ISO-style timestamp without a timezone offset. The portal's timezone has not been independently confirmed, so the API does not append `Z` or an assumed offset.

## 4. Public API Versus Upstream Portal

The public API implemented in this project exposes these routes:

| Public API route | Purpose |
|---|---|
| `GET /health` | Local service health |
| `GET /meters?q=&page=1` | Search meter summaries |
| `GET /meters/{meter_id}/location` | Retrieve meter coordinates |
| `GET /meters/{meter_id}/energy` | Retrieve normalized energy readings |
| `GET /openapi.json` | OpenAPI specification |
| `GET /docs` | Swagger UI |

These routes are not the same as the portal's upstream routes.

The public API uses a normalized JSON contract, validates input, handles upstream sessions, and maps failures to consistent error responses. It does not expose the upstream session cookie to callers.

## 5. Authentication and Session Behavior

### Directly Observed

- Login is submitted to `POST /login`.
- The form field names are `email` and `password`.
- The login response body indicated a redirect to `/meters`.
- Browser navigation after login reached the meter list.

### Implementation Behavior

The API client:

- Logs in when an upstream request requires an authenticated session.
- Reuses the session cookie for subsequent upstream requests.
- Shares the first login among concurrent requests.
- Attempts one re-login and retry when the upstream indicates that the session has expired.
- Avoids retry loops after persistent authentication failures.
- Does not return session cookies or credentials to API consumers.

These are behaviors implemented and covered by automated tests. The tests use a fake upstream and do not prove that every session-expiry behavior will remain unchanged on the live portal.

### SvelteKit Observation

The portal response included a `__data.json` request whose payload had a framework-style data structure. This is consistent with SvelteKit page-load data. The current API does not parse that structure.

The implementation sends an `Origin` header for the login form request and checks for a session cookie rather than treating any HTTP 200 login response as sufficient proof of successful authentication.

## 6. Response Normalization

The portal response fields and public API fields differ intentionally.

| Upstream representation | Public API representation |
|---|---|
| `meterId` | `meter_id` |
| `serialNo` | `serial_no` |
| `phaseType` | `phase_type` |
| `installStatus` | `install_status` |
| `dtCode` | `dt_code` |
| `voltR` | `volt_r` |
| Numeric strings | Numbers when valid |
| `DD/MM/YYYY HH:mm` timestamp | ISO-style local timestamp plus `timestamp_raw` |

The parser follows these rules:

1. Invalid timestamps are treated as upstream data errors because the reading cannot be reliably placed in time.
2. Missing or invalid individual measurements become `null`, never silently `0`.
3. Invalid or out-of-range coordinates are rejected as upstream data errors.
4. Unexpected response shapes are treated as upstream data errors.
5. Raw upstream error bodies and authentication details are not exposed to API consumers.

## 7. Assumptions and Unknowns

The following details have not been fully verified and should not be treated as confirmed portal guarantees.

### Timezone and Units

- The portal displays day-first timestamps.
- No timezone offset was observed in the timestamps.
- The exact timezone has not been independently confirmed.
- The labels KWH, KVAH, and V(R) are visible in the UI, but the portal's detailed unit definitions have not been independently documented.

### Search Pagination

The observed request includes `q` and `page` parameters. The following details remain unverified:

- Exact page size
- Complete pagination metadata
- Behavior for page numbers beyond the final page
- Behavior for a query with no matches

The public API does not invent upstream pagination metadata.

### Energy Filtering

The observed energy request returns readings for the selected meter. Date-range filtering or upstream pagination support has not been confirmed. The public API therefore does not claim that such filtering is available.

### Meter Detail and Hierarchy

The portal UI exposes additional nameplate fields and the distribution hierarchy. The current API does not expose those fields as separate endpoints. The framework page-load data has not been parsed into a stable public contract.

### Data Semantics

The sample energy readings rise over time, but that observation alone does not establish all meter counter semantics or guarantee monotonic values for every meter.

## 8. Configuration

The upstream settings are supplied through environment variables in `.env`.

The observed values are:

```env
UPSTREAM_BASE_URL=https://urja-ops.flockenergy.tech
UPSTREAM_LOGIN_PATH=/login
UPSTREAM_LOGIN_USER_FIELD=email
UPSTREAM_LOGIN_PASS_FIELD=password
UPSTREAM_SEARCH_PATH=/portal/meters/search
UPSTREAM_GEO_PATH=/portal/meters/{meter_id}/geo
UPSTREAM_ENERGY_PATH=/portal/meters/{meter_id}/energy
```

`{meter_id}` is replaced with the URL-encoded meter ID.

The project retains the configuration variable name `UPSTREAM_USERNAME` for the login value even though the portal form field is named `email`.

Credentials must be entered locally in `.env`. They must not be included in this document, `.env.example`, source control, screenshots, or logs.

## 10. Limitations and Future Investigation

The current implementation prioritizes the core read-only API. The following work remains possible:

- Expose verified meter detail and network hierarchy data.
- Establish exact pagination and no-match behavior.
- Confirm timestamp timezone and measurement semantics.
- Investigate date-range filtering.
- Add contract tests using sanitized live response fixtures.
- Add caching only after defining acceptable staleness.
- Add structured request logging without secrets.
- Revisit upstream behavior when the portal changes.

The implementation should remain read-only unless the assignment's scope and authorization explicitly change.
